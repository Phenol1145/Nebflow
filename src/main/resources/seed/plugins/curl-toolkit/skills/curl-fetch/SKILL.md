# 原始 HTTP 取数纪律（curl-fetch）

你被分配了 curl-toolkit 插件，节点会话里有 **Curl**（原始 HTTP 请求工具）。
本 skill 只立三条纪律：什么时候用 Curl、什么时候不用、用的时候怎么用。

## 一、Curl vs WebFetch 分流（先判这个，再动手）

| 需求 | 用哪件 | 理由 |
|------|--------|------|
| 读网页正文（文档页、文章、README 渲染页） | WebFetch | 已做正文提取，直接可读；Curl 会取回整页 HTML 噪音 |
| 调 REST/JSON API、取结构化数据 | Curl | 要的就是原始响应体 |
| 看响应头 / 状态码 / 重定向链 / 缓存与内容协商行为 | Curl | WebFetch 只给正文，协议面细节被丢掉 |
| 下载非 HTML 文件（JSON / CSV / 压缩包 / 二进制） | Curl | WebFetch 面向 HTML 正文阅读 |
| 需要自定请求头、方法（PUT/DELETE）、请求体 | Curl | WebFetch 是「取网页」，不是通用 HTTP 客户端 |
| 需要浏览器登录态、跑 JS 才能出内容的页面 | 都不行 | 明确上报缺能力，勿硬试 |

判据一句话：**要协议面或非 HTML 正文 → Curl；要「像人一样读网页」→ WebFetch**。
两件都有时按上表分流；只有 Curl 时，对 HTML 页面先用 Curl 取回后再自行剥正文，
并把「未经正文提取」这一事实写进产出。

## 二、Curl 使用规范

1. **先想清楚要什么再发**：URL、方法、必要请求头（Accept / Content-Type /
   鉴权头）一次到位，避免试探性连发。
2. **响应三看**：状态行（非 2xx/3xx 先停手判断）、响应头（Content-Type 决定
   怎么解析；重定向看 Location）、正文（按 Content-Type 解析，勿盲当文本）。
3. **鉴据纪律**：鉴权凭据只来自任务输入或环境配置，不得虚构、不得写进产出；
   报错信息里的凭据先打码再引用。
4. **体量纪律**：大响应（列表接口、文件下载）先看 Content-Length，取需要的
   分页/片段，不整页倒进上下文。
5. **失败是信息**：超时 / 4xx / 5xx 要读响应体里的错误说明并如实上报，不得
   静默换 URL 重试掩盖问题。

## 三、产出引用要求

- 引用取回的资料时给出处 URL 与关键响应事实（状态码、Content-Type、取数时间）。
- 原始 JSON 片段引用保持逐字，不得转述成「大约是」。
- 协议面结论（如「该端点 301 到 https」「响应是 gzip 的 JSON」）必须来自你实际
  看到的响应头，不得推测。
